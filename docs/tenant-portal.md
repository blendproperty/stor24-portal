# My STOR24 tenant access

## Customer journey

Open `/my` (or the public website's My STOR24 link), enter the email already verified on the customer record, request the six-digit code, and sign in. Customers see only matching, verified records in the configured organisation. Multiple accounts using that verified email are shown together. Codes expire after ten minutes, allow five attempts, and are single-use. Sessions end after thirty minutes; signing out revokes the current session.

Customers can select a date range, view their ledger statement, download a branded PDF, or email a secure portal link to their own verified address. A forwarded link is not an access token: the recipient must sign in and pass the same customer ownership checks. Available completed signed agreements and successful-payment receipts are downloadable; previously issued invoice/statement HTML files are retained in their original issued format. No invoice, payment or charge is generated by viewing or downloading.

## Staff journey

Operations → Accounts → choose account → Account statement. `ledger.view` and current organisation/facility permissions govern viewing/PDF downloads. Email secure link requires `billing.documents.send`, a separate confirmation and a verified customer email. The server chooses the recipient; the browser cannot substitute another email address.

## Configuration and boundaries

- `APP_URL` must be the canonical HTTPS CRM origin.
- `AUTH_SECRET` must contain at least 32 characters.
- `TENANT_PORTAL_ORGANISATION_SLUG` selects the default organisation. The production compose file defaults to the verified existing `stor24` slug. Explicit organisation links remain scoped to that organisation.
- Existing transactional email provider credentials are used. Provider acceptance is not inbox-delivery proof.
- Apply migration `20260910160000_tenant_portal_access` before serving the feature.
- Challenge/session tokens are stored only as hashes. Tenant cookies are distinct from staff cookies, HTTP-only, Secure in production and SameSite Strict. Every data request rechecks organisation, captured customer IDs and currently verified email.
- Atomic database rate limits cover sign-in, verification, downloads and email delivery. No browser/PWA caching of account responses. Audit events record sign-in, sign-out, account views, downloads and statement-link delivery without recording OTPs.
- Expired challenge/session records are removed after a 24-hour troubleshooting window when another code is requested. Business records and audit events are unaffected.
- Changing/removing the verified email prevents old sessions from reading that customer's records. Emergency session revocation can set `TenantPortalSession.revokedAt`; no staff self-service revocation screen is included in this release.
- Ledger opening balances/imports, historical invoices, provider settlement, VAT/legal approval, production charging and staff training remain separate programme gates. This feature does not reconcile accounting data or certify provider settlement.

## Verification

`npm run test` includes cryptographic/scope, OTP single-use/attempt/expiry and session tests. Service tests use isolated database doubles and do not prove live email delivery. `scripts/tenant-portal-browser-check.mjs` exercises synthetic desktop/phone journeys with all tenant API traffic intercepted; supply `TEST_RUNTIME_PACKAGE` for an installed Playwright runtime. The script is localhost-only and sends no email. `scripts/tenant-pdf-preview.ts` generates a synthetic multi-page layout PDF under ignored `output/`.

Before calling the feature live-verified, confirm deployment/migration, unauthenticated rejection, an authorised real email-code sign-in, own-account statement/download accuracy, rejected foreign-account access, logout rejection, and provider/inbox delivery of an explicitly requested secure statement link. Do not create financial transactions for these tests.

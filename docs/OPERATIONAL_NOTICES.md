# Editable operational notices

Communications → Operational notices implements the trading-hours, immediate-closure and maintenance examples in Faeez's Form Setup recording. Existing fixed collection/payment/lease templates remain separate. No source attachment, historic recipient, other-brand wording or unapproved site instructions are imported.

Choose a permitted store. Start from a neutral draft example, edit its name, subject and plain text, and save a version. Existing `CommunicationTemplate` records retain immutable versions; old versions are readable and cannot overwrite a newer version. The library shows the latest 200 version records for the store. Saving a new version invalidates unsent approvals based on its predecessor. This does not change actual trading hours, access settings, physical closure, rent or emergency procedures.

Variables are explicit: `{{customer_name}}`, `{{store_name}}`, `{{notice_date}}`, `{{effective_time}}`, `{{details}}`, `{{contact_details}}`. Customer/store names come from the current permitted source. The other four fields are mandatory, bounded staff inputs. Unsupported/malformed variables, control characters and subject header injection are rejected. HTML is literal text, safely escaped for email; raw HTML/RTF authoring and automatic SMS/WhatsApp translation are outside this implementation.

Save template edits before previewing. Select each intended customer (maximum 20). No implicit whole-store audience exists. Search displays up to 50 matching current ACTIVE/NOTICE_GIVEN customers; narrow the name/company search for further results. Selections persist across searches and can be cleared explicitly. Preview renders the exact complete selected audience. Verified customer email, explicit current email consent and no recorded consent opt-out are mandatory. Every required store, template, recipient, rendered message and consent source is fingerprinted; changes require fresh review. Multiple tenancies for one customer do not create duplicate emails. Distinct customer records sharing an address remain distinct explicit recipients and must be reviewed accordingly.

Save reviewed draft sends nothing. An authorised colleague who neither prepared the notice nor edited any version of its template must review every message and the full audience and enter an approval reference. Software records that review; it cannot establish that the wording, timing or business policy has been approved outside the app. Template versions, encrypted message snapshots, exact recipient IDs, review references, immutable audit events and outcomes use existing storage. Identical previews deduplicate to one notice, including after acceptance; a deliberate new notice needs changed explicit content/date/source, not a retry.

The existing `operations.view` scope reads the library. Current `operations.manage` for the exact store is also required for editing, preview, preparation and review. Sending additionally requires current `billing.documents.send` for that same store. No role, permission grant or invitation is changed. Normal staff sessions, MFA, same-origin mutation checks, bounded requests, rate limits and private/no-store responses remain mandatory. The authorising user and independent approver must retain current active access before delivery.

After separately obtaining business/channel approval, a permitted operator confirms and sends **one next approved recipient at a time**. Read that named recipient and expanded exact message before confirming. Each send commits its durable claim, CommunicationLog and audit before calling the existing DLP-protected email provider. A concurrent/repeated request does not call the provider twice. No background operational-notice sender or schedule is added. Provider acceptance is not inbox delivery/read confirmation.

An uncertain send or persistence failure holds the notice in SENDING/REVIEW_REQUIRED and prevents automatic or manual blind replay through this workflow, including the remaining audience. Investigate provider evidence and duplication risk separately. Unsent notices can be cancelled; a partially dispatched notice can cancel its remaining unsent recipients when no provider attempt is in progress. Cancellation never recalls an attempted email or erases its outcome. A source change can also hold remaining recipients after a partial send. Do not create a replacement notice to bypass an uncertain attempt.

The latest 20 saved notices show exact retained messages and recipient outcomes. The existing Message delivery history and per-customer History & notes retain delivery records and redacted message evidence beyond that list. These follow current store/customer permissions. No new document download, financial posting, collection, legal, physical-access or real customer message is performed during development tests.

Business/Faeez approval of actual wording, audience, contact/source accuracy, timing and channel; provider sender/consent/delivery acceptance; real staff/device/accessibility/Word/printing acceptance where relevant; laptop/Outlook/MFA/training and all existing security/recovery gates remain open. Preview/review records and synthetic tests do not close those gates.

# Daily internal arrears reviews

This feature prepares an internal Operations review task. It does not send a letter, post a fee, approve a financial change, restrict access or restore access. The fee amount remains unset pending Liezl/Mark.

For an active EFT/card account, an authorised staff member opens Collections, records a case note, selects the explicit start/end dates and South African time, confirms internal task preparation and saves the plan. Up to93 calendar days are supported, including weekends. A current Collections and Operations viewer/manager at that store is required to create or change the delegation. Cancellation remains available if the account later changes payment method.

The worker checks current authority, active tenancy, approved due dates, reconciled outstanding debt, receipt evidence, disputes, promises and adjustments. Seven calendar days run from the agreed EFT/card due date. Debit-order cases remain held because an authoritative final-failure-to-original-charge feed is not implemented. Pending, failed or unposted outcomes cannot be overridden by scheduling.

The visible last evaluation is distinct from saving a plan or enabling a setting. The worker handles at most 25 due plans per invocation, with bounded connection/transaction/statement waits and an execution budget. A signed organisation-scoped scan cursor advances before attempting those plans and wraps when necessary, so invalid or failed plans cannot permanently hide later healthy plans. Cursor advancement records selection, never task completion. The five-minute timer supplies further invocations. A chosen time is the start of eligibility for evaluation, not a guaranteed processing SLA. Missed runs use current-day evidence and do not manufacture historical approval. No production capacity or human acceptance is implied by isolated checks.

Both manual and timed preparation use the same account lock and oldest-unpaid-charge task identity. Closed tasks stay closed. Unchanged existing tasks are not duplicated or repeatedly written into case history. Automated activity is labelled as scheduled delegation; system audit records have no human actor. Task, case activity/version, plan outcome and audit commit together or roll back together. Every run rechecks the delegating user's current same-organisation, same-store permissions. Plans and outcomes are encrypted and signed; mismatched stored metadata fails closed.

## Configuration and release stages

Code defaults to disabled. The dedicated `ARREARS_REVIEW_SCHEDULE_ENABLED` setting, explicit `ARREARS_REVIEW_ORGANISATION_ID` and a private `ARREARS_REVIEW_WORKER_KEY` of at least 32 characters control only this worker. They do not enable the separate collections email scheduler or any financial/provider feature. The existing integration vault key protects saved plans and signs scan progress. Creating/configuring the persistent bearer credential and activating ongoing worker access require specific action-time owner approval; broad software-rollout authority does not substitute for it. No real credential has been created or configured by this source change. Never publish the keys or place the worker key in process arguments.

After protected source/main checks and the normal application deployment, the operator verifies the exact deployed ref before installing `docs/stor24-arrears-review.service` and `.timer` under `/etc/systemd/system/`, then reloading systemd and enabling the timer. Its script runs inside the deployed app container, reads the key from that environment and calls only the internal review endpoint. It logs counters, not customer data or credentials. Configuration, timer status, service outcome, actual plan/run/task evidence and staff acceptance must each be recorded separately in PROJECT_CONTEXT.md. A successful empty run is not proof of a real customer task or staff acceptance.

Do not enable `COLLECTION_SCHEDULE_ENABLED`, `STAFF_EVENT_EMAIL_ENABLED`, Netcash preparation/lookup/sandbox flags or physical-access integration as part of this feature. Provider final-result contracts, legal notice wording, separately authorised access approval/execution/restoration, fee policy/posting and customer-channel sends remain independent unfinished work and approval gates. Previously passed meeting checks remain passed; no mandatory Faeez-only repeat is introduced.

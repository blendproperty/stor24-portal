# Tenant rate review and Word report exports

30 October 2026 implementation candidate, following Faeez's 29 October email, Tenant Rate Management recording and report catalogue screenshot. Release and live availability must be established separately in PROJECT_CONTEXT.md. Business approval and staff/device acceptance remain open.

## Tenant review

Use **Billing → Rent reviews** with the existing Organisation owner access. No staff grants are changed by this implementation.

1. Choose a store and **View duration report**. Compare current rent, standard monthly unit rent, recorded area, size occupancy and variance. Historical last-change dates remain unknown unless a recorded schedule establishes them.
2. Choose completed-month eligibility, the existing percentage/rand increase rule and a future effective month. **Preview group increase** calculates suggestions using that entered rule and cent rounding. It does not automatically target standard rent or infer a new increase policy from occupancy.
3. Explicitly select eligible tenants, individually or using **Select all eligible shown**, then preview again. Every selection/filter change invalidates approval. No tenants are selected by default. The server rejects unknown/cross-store selections and refuses a selected audience containing ineligible rows.
4. Supply the required pricing approval/tenant-notice reference and confirmation for exactly that selected audience before scheduling. The existing minimum-notice interval, future effective dates, stale-preview protection, serializable transaction, approval audit and billing-rate schedule remain in use. An invoice is not posted and a customer notice is not sent by this step.
5. **Dismiss** an exception with a reason, or inspect the **Dismissed** view and **Restore** it with a reason. Status persists per occupancy until explicitly changed. Both transitions are audited and use optimistic conflict checks. Dismissal excludes a tenant from new reviews; it does not cancel an already approved scheduled increase or change billing. A newly restored tenant requires a fresh preview and selection.

Review state uses the existing ConfigurationProfile store under OCCUPANCY_RENT_REVIEW; rent schedules remain under OCCUPANCY_RENT_SCHEDULE. No new schema migration is required. Status/audit writes roll back together. Closing or transferring an occupancy does not transfer its review state to a new occupancy.

### Benchmark definitions

| Field | Definition and boundary |
|---|---|
| Standard rent | Current Unit.monthlyRate, separately from the occupancy's current/scheduled rent. This is a current benchmark, not a reconstruction of a historic standard rate. |
| Size | Positive recorded UnitType.areaSqMetres. Missing/zero areas remain unknown; width/length or a type's name are not invented as area evidence. |
| Size occupancy | Current units marked OCCUPIED divided by all standalone units of the same recorded area in this store. Different type names with the same recorded area share the group. Service/unavailable units and closed floors remain in the denominator; combined component units and other stores are excluded. This is explicitly separate from the operational-floor occupancy report. Source status correctness remains a data acceptance gate. |
| Variance | Current rent minus standard rent, rounded to cents. Percentage is `(current / standard - 1) * 100`; zero standard rent or non-ZAR account currency leaves the percentage unknown. Non-ZAR amount variance is also unknown. |
| Suggested rent | Existing entered percentage/rand increase applied to the effective-period rate. Caps, exceptions, escalation policy, tax/standard-rate interpretation, legal notice acceptance and real customer approval remain business decisions. |

The protected rent-review CSV and fixed Tenant duration report also include the new benchmarks/status. Review reasons remain available in the owner review and its protected CSV/audit trail. Source/benchmark drift, review-state changes or a changed selection invalidate the approval fingerprint. Existing historical approval payloads remain readable when the new explicit-selection field was absent.

## Word reports

Select **Word (.docx)** in the existing fixed report, visual builder/online report, saved-report bundle or retained snapshot download controls. The current recurring-charge projection retains its existing CSV/JSON-only contract and CSV backup interface.

- Word files contain editable WordprocessingML, generated by the existing server ZIP helper without adding a dependency. They contain literal text, not executable fields, macros or external relationships.
- The full selected result is retained with title, period/source basis, generation time, record count and confidentiality label. Up to six columns use a table with repeating headings; wider results use labelled records. Short rows stay together, long text can paginate, and empty visual reports retain their selected headings and an explicit no-matches message.
- Retained snapshots keep their captured source basis/generation time. Changing a report's dates or export format does not invent historical data or future projections. Qualified imported-history datasets remain separately labelled.
- Existing report/export and personal-data permissions, store intersections, current-role rechecks, DLP classification/secret filters, private headers and export audit apply to DOCX. Fixed reports now recheck both report and export scope before release, including store moves during generation. Rendering errors/size expansion return a controlled response. Word output and bundles remain bounded by the existing 5 MiB limit.
- Verify the output's selected fields, source/date basis, row count, values and reconciliation before business use or onward sharing. Edits to a downloaded Word file do not update source records or establish approval.

## What is checked

- Accounts: `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/gshadow` (including password-hash and group-membership changes).
- SSH keys: default `authorized_keys`/`authorized_keys2` and `.ssh` directory metadata for root, UID >=1000 and login-capable system accounts; `/etc/ssh/stor24-keys`, `/etc/ssh/stor24-cms-keys`; default RSA/ECDSA/Ed25519 public server host keys. The actual custom service key paths were confirmed through read-only `sshd -T` inspection.
- Settings: sshd configuration/drop-ins, sudoers/drop-ins, persistent UFW configuration, PAM, `/etc/security`, Docker daemon configuration and the STOR24 web/CMS privileged release handlers/libraries named in `scripts/check-host-security.mjs`.

Only SHA256 fingerprints and file/directory ownership/mode are retained locally. Password files are read locally for hashing; their contents and private SSH keys are not published or logged. Private host/personal SSH key files are not read. The baseline contains sensitive inventory/fingerprints and must remain root-only, outside Git. Symlinks, unsupported entries, oversized files/inventories, malformed accounts and unavailable/corrupt/permissive baselines produce an unavailable finding, never a healthy result.

The local baseline is `/var/lib/stor24-security/baseline.json` (root,0600; parent root,0700). Initialization uses exclusive creation and refuses to replace an existing baseline. A read check never initializes or updates it.

Baseline version 2 ignores lines consisting only of spaces, tabs or carriage returns in authorised-key files. All bytes of non-blank lines and all path, ownership and permission checks are retained. Server host keys and other monitored files still use byte-for-byte fingerprints. Version 1 continues to use its original fingerprints. For an upgrade, verify the version 1 comparison is clean, preserve the version 1 file in protected storage, and compare the candidate version 2 inventory against the reviewed version 1 state before activation. For rollback to a version 1-only checker, restore the matching protected version 1 baseline and then verify its report.

## Reporting and retained findings

The version-1 heartbeat accepts an optional `security` state for a backwards-compatible receiver-first rollout. Exact flags are `STOR24_SECURITY_CHANGES_ENABLED=true` in the root host monitor environment and `STOR24_SECURITY_CHANGES_REQUIRED=true` in the production GitHub repository variables. Invalid values fail closed. Once required, a legacy report without a security state is unavailable.

Fixed categories are `STOR24_ACCOUNTS_CHANGED`, `STOR24_SSH_KEYS_CHANGED`, `STOR24_SECURITY_SETTINGS_CHANGED` (HIGH) and `STOR24_SECURITY_CHECK_UNAVAILABLE` (WARNING). Simultaneous backup/resource findings remain visible and keep their higher severity where applicable. No filenames, usernames, key fingerprints or file contents cross the host/report boundary.

The Worker retains each detected category separately in the existing evidence namespace at `security-findings:<MARKER>`, without TTL. Independent fixed category keys prevent concurrent uploads or stale reads from erasing another category. Healthy uploads cannot clear them, and the host bearer protocol cannot delete them. GET host combines these categories alongside the latest report; the external checker alarms after local restoration or a stale heartbeat. A legacy `security-findings` record, if present, is also read and preserved. Cloudflare KV is eventually consistent: visibility and first-receipt timestamps are approximate, and this is not a transactional incident ledger. Review/export through trusted provider access before any explicit acknowledgement. Do not automatically clear, expire or accept a finding.

The timer samples approximately every five minutes; the independent monitor polls approximately every ten minutes. Existing global 30-minute notification suppression remains in place and can delay a new security notification while another alert is active. Scheduler delays and KV propagation also apply: no fixed alert-delivery SLA is claimed. A change made and reversed entirely between samples can be missed. This is selected-file drift detection, not auditd/event capture, malware scanning or proof that a baseline is clean. A root attacker can tamper with the local collector/baseline or forge heartbeats; an independently missed-heartbeat watchdog remains a separate open control. Runtime iptables, arbitrary cron/systemd persistence, cloud account configuration and CRM/CMS application account events are outside this first-stage scope.

## Response, acknowledgement and rollback

A HIGH finding means a selected file changed, not that compromise is established. Preserve evidence; compare root-only before/after fingerprints and planned maintenance records, inspect through a trusted administration path, and apply the separate emergency isolation plan if incident triage warrants it. Do not automatically turn on the emergency blocking rule, revoke access, restore data or rotate credentials through this detector.

For an authorized lasting change, retain/export the old baseline and findings securely, review the new state, and explicitly approve rebaselining and acknowledgement. Move the old baseline to protected incident storage, initialize a new one and verify the report. An authorized Cloudflare namespace owner may then remove only the reviewed `security-findings:<MARKER>` keys (and legacy `security-findings` if applicable) after evidence export; deletion must be followed by an authenticated remote readback and subsequent poll. Rebaseline first so the next host upload cannot immediately re-latch the change. The public Worker deliberately has no acknowledgement API. Never remove the whole namespace or ordinary backup/resource/dashboard evidence.

Rollback is also a live decision: preserve any finding before changing flags. Revert the host current symlink/environment to the recorded prior version, and revert the receiver only after recording its retained findings. If the required consumer flag remains true, the old producer correctly reports unavailable. Removing that requirement disables this coverage and must be explicitly recorded/approved. Other host checks must remain active. No reboot, customer-data operation, database privilege change or root SSH cutover is included.

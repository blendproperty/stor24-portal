## Dated implementation history

14 October 2026. The existing REST-shaped DebiCheck scaffold has no source callers and is not an operational provider integration. The new SOAP module prepares the documented authentication fields and performs the documented current-contract status lookup. It is a foundation for the reviewed workflow, not a finished staff/customer feature.

The current NIWS_NIF service definition confirms `DebiCheckAuthenticate` with its exact ordered fields, Boolean identity/first-amount flags, named bank account enum, compact collection date, `collectionDayCode` and debtor identity enum. Preparation validates these fields, escapes text and never submits them. Netcash requires a minimum three-minute timeout for TT1 authentication; a future durable submission worker must own that call, rather than blocking a normal web request or repeating a timeout.

`DebiCheckAuthenticationCurrentStatus` uses the Debit Order service key and the original `NC` contract reference. Its SOAP action is `http://tempuri.org/INIWS_NIF/DebiCheckAuthenticationCurrentStatus`. The current WSDL returns a structured result rather than the documentation's illustrative MethodParameters wrapper. The reader bounds the result, matches the original contract, handles nullable cancellation fields and distinguishes rejected/unknown/cancelled states. An observed Accepted state is neither collection authorisation nor a paid receipt. No service key, raw XML, bank or payer identity is returned by the reader.

Before exposing these helpers, the system still needs store/account-owned contract and verified-template records, source-bound consent and independent review, encrypted payer data, a durable single-attempt submission worker, uncertain-outcome reconciliation, native customer/staff controls and audited status updates. Collection requires the separate documented batch contract, retained authenticated mandate evidence, reviewed invoices and approved collection dates. This increment supplies no bank request, collection, migration, provider activation, ledger posting or customer message. The legacy scaffold remains unverified; its callers must not be introduced as a shortcut.

Automated transport is mocked. Actual approved developer template/contract, payer bank authentication, rejection/cancellation, asynchronous status, collection and reconciliation acceptance remain open, alongside production company onboarding and finance/data/training approvals.

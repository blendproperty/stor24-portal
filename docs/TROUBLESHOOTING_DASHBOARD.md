# Owner troubleshooting dashboard

Open **Settings → Troubleshooting** (`/settings/troubleshooting`). Brett is the sole responder; no role is assigned to Mark or CloudSphere IT. Refresh reads health and aggregate evidence only. Download diagnostics excludes recipient details, provider credentials/configuration, customer records and raw logs. No restart, backup deletion, financial/provider retry or customer write is offered.

Website and database cards describe the current authenticated request and read-only SQL probe. The one-minute host timer collects disk use, available memory, current container health/OOM state, released image and aggregate PostgreSQL connections. It uses fixed Docker/read-only SQL arguments with bounded execution/output, not a web-triggered command or Docker socket exposed to the application. It atomically saves `operations.json` in the existing read-only backup status mount. Missing/invalid or older-than-three-minute host evidence is explicitly unverified. Disk85%, available memory10% and connection80% correspond to existing external failure thresholds; disk75% and memory20% add early review hints.

The normal deployment installs `stor24-operations-status.service`/timer and refreshes after app activation. `/usr/bin/node` and `/opt/stor24-crm` are the existing Hostinger runtime/checkout. Status files contain aggregate operational metadata only and are readable by the existing app account. No new app volume, Docker socket, server credential, provider or database migration is introduced.

The external monitor publishes a sanitised result over its existing protected SSH connection after dispatch. The server writer admits numeric run IDs, expected states, bounded channel acceptance/failure counts and timestamps only; contacts, message bodies, provider identifiers and secrets are dropped. It retains the latest20 checks and deduplicates run IDs. Dashboard cards mark monitor evidence older than30minutes unverified; ten-minute GitHub scheduling is not guaranteed. Publishing evidence can fail independently of checks or sends; inspect the actual run link. Deployment-before-first-new-run may legitimately show no history. Existing history is not invented or backfilled as live checks.

Integration evidence is organisation-scoped and selected without credentials/config/raw failure strings. Connection records older than24hours or never checked are labelled stale/untested. Messaging environment presence means configuration only; queue counts are organisation-scoped actual counts. Neither proves a fresh provider/device UAT. Recipient count is aggregate only.

Page/API require current organisation-owner access and a configured matching monitored organisation. Missing organisation binding fails closed, preventing host evidence disclosure to other organisations. Responses are private/no-store. Bounded local status-file reads, connection row limit30, history20 and existing database deadlines constrain inspection. Filesystem evidence failure or an individual database query failure preserves independent checks with unknown/failed indicators rather than making every panel green.

If the website or authentication database is down, this dashboard can also be unavailable. Use existing external email/SMS/WhatsApp alerts and GitHub monitor as the independent route. A stale indicator is evidence for investigation, not a second independent stopped-monitor notification system. No full recovery, provider/device UAT, training or business acceptance gate is closed by this dashboard.

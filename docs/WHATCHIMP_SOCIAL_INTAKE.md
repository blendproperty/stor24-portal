# Facebook and Instagram enquiry intake candidate

This candidate is separate from the established WhatsApp intake. It is not configured or live until deployment, dedicated credential provisioning, WhatChimp mapping, and end-to-end tests have been completed.

## Contract

`POST /api/integrations/whatchimp/social` accepts JSON or bounded native form-data/urlencoded fields and a dedicated `Authorization: Bearer` key. Each READY `WHATCHIMP_SOCIAL_INTAKE` profile contains `enabled`, `channel` (`facebook` or `instagram`), `botId`, SHA-256 `keyHash`, `facilityId`, and `recipientUserId`; organisation and facility are derived from the profile, never from the request. Use independent keys and profiles for Facebook and Instagram. The selected recipient must be an active user with `leads.view` for the facility. These keys authorize creation of prospective enquiries, not access to customers or account data. Do not reuse the WhatsApp key.

Actions: `probe` is no-write. `start` creates a short-lived capture session and returns an unpredictable `enquiryKey`. `validate` accepts `phone` and returns `VALID_PHONE` or `INVALID_PHONE` without creating a lead. `submit` requires `enquiryKey`, `name`, `phone`, `requirements`, and `startDate`. It repeats validation and returns `SUBMITTED` and the CRM reference only after an atomic lead, follow-up task, session and pending notification are saved. Matching replays return the same lead; changed replays are rejected. Capture expires after seven days. The phone check recognizes South African national numbers and explicit international numbers; it is a format check, not proof of ownership, assignment or reachability.

WhatChimp must map each response to a dedicated field, reset the result checkpoint before each request, branch only on the expected literal phase, reprompt on `INVALID_PHONE`, and provide a manual contact route on request failure. Never claim CRM receipt merely because the request was attempted. Do not send raw customer text via JSON interpolation. The provider's mapping, branch behavior, retry behavior and simultaneous conversations require tests on each channel.

The pending notification contains a staff CRM link rather than customer contact details. A durable `SENDING` claim precedes the provider call; accepted means provider acceptance, not inbox delivery. Uncertain sends become `REVIEW_REQUIRED`, and an interrupted `SENDING` claim is never automatically repeated. The existing authenticated lead-SLA worker also processes pending social notices; its timer and organisation configuration must be verified. Operational review of stuck/failed notices and a staff monitoring owner remain required. There is no user interface yet to inspect or retry notice states, nor an automated reconciliation of ambiguous sends.

## Release and validation gates

Review code and security, pass CI and isolated transaction tests, merge and use the normal release process. Confirm the deployed version and no regression to WhatsApp or the existing SLA worker. Provision separately scoped credentials only after explicit approval for the new persistent WhatChimp access; verify recipient and facility scope. Configure provider inputs, all phase guards and failure branches, then run no-write probes. Test labelled valid, invalid, duplicate, timeout and concurrent enquiries on Facebook and Instagram; verify lead source, phone, task, provider acceptance and Katlego's actual mailbox receipt. Do not count fixtures as business leads. Until all gates pass, team members must monitor social inboxes and the existing Facebook input report manually. Preserve all other existing UAT, provider, data, privacy, training and approval gates.

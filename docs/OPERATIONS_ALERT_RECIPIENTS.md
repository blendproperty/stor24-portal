# Operations alert recipients

Organisation owners manage the response team at **Settings → Operations alerts** (`/settings/alerts`). Add up to 20 people/addresses; choose email, SMS and WhatsApp independently; record permission to receive notifications; pause or remove a recipient. At least one active channel must remain. Nothing is sent merely by saving the list.

The list is organisation-scoped in the existing ConfigurationProfile store under the reserved OPERATIONS_ALERTS domain. Changes and their count-only audit commit together; concurrent owner changes return409 instead of overwriting. The general configuration endpoint neither exposes nor modifies this reserved profile. Owner administration uses live role checks, same-origin writes, rate limiting and no-store responses. New recipients still need an explicitly agreed delivered test and responder training.

The external GitHub monitor reads the list over HTTPS at the exact dedicated `/api/v1/operations/alert-monitor-config` endpoint. It requires `STOR24_ALERT_CONFIG_KEY` (random32byte hex), shared only between the app's protected environment and the GitHub production environment secret. `STOR24_ALERT_ORGANISATION_ID` binds the reader and administration page/API to the monitored organisation. Neither value is returned to the admin browser. Missing/wrong credentials return401 before data access; arbitrary organisation query strings are ignored. Provider credentials remain in the existing server/GitHub secret stores.

On each successful read, the runner encrypts the list with AES256GCM into `.operations-alert-config.enc`; a unique per-run GitHub cache entry restores the latest available copy for future runs. Encryption key derivation is domain-separated from the bearer credential. No recipient details go into logs or result artifacts; reports contain channel, pseudonymous recipient reference and provider acknowledgement only. Four recipients are dispatched concurrently; independent channels preserve partial results and uncertain POSTs are never replayed automatically.

If the website/config reader is unavailable, the runner uses the encrypted last-known list (maximum age30days). GitHub cache storage is best effort and may evict inactive entries. If no valid encrypted copy is available, emergency notifications retain the existing confirmed Brett email/mobile GitHub variables. Changes, pauses and removals cannot reach an unavailable reader until it becomes reachable; allow the next successful monitor cycle to refresh the encrypted copy. The site should not be the sole place emergency contacts can be recovered. During key rotation, update both protected environments and verify a fresh configuration read/cache before relying on fallback.

Deployment uses the normal exact-main release checks and backup/build/versioned migration procedure. No new schema migration is required. Bootstrap only the confirmed Brett recipients; no invented team member or customer recipient. Verify anonymous admin/reader rejection, owner read/write, configuration source SAVED_RECIPIENTS in a real external monitor run and provider delivery of an explicitly labelled test. Isolated browser/SQL tests are separate evidence from live owner UAT and physical recipient acknowledgement.

Healthy silence, failure/recovery notifications and existing cooldown remain. This release does not make GitHub cron a guaranteed10minute SLA, add a second stopped-monitor watch, establish response/escalation timing or close backups, keys, provider/device UAT, staff training or business approval.

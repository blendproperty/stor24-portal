# Operations alert recipients

Organisation owners manage the response team at **Settings → Operations alerts** (`/settings/alerts`). Add up to 20 people/addresses; choose email, SMS and WhatsApp independently; record permission to receive notifications; pause or remove a recipient. At least one active channel must remain. Nothing is sent merely by saving the list.

The list is organisation-scoped in the existing ConfigurationProfile store under the reserved OPERATIONS_ALERTS domain. Changes and their count-only audit commit together; concurrent owner changes return409 instead of overwriting. The general configuration endpoint neither exposes nor modifies this reserved profile. Owner administration uses live role checks, same-origin writes, rate limiting and no-store responses. New recipients still need an explicitly agreed delivered test and responder training.

The external GitHub monitor reads the list over HTTPS at the exact dedicated `/api/v1/operations/alert-monitor-config` endpoint. It requires `STOR24_ALERT_CONFIG_KEY` (random32byte hex), shared only between the app's protected environment and the GitHub production environment secret. `STOR24_ALERT_ORGANISATION_ID` binds the reader and administration page/API to the monitored organisation. Neither value is returned to the admin browser. Missing/wrong credentials return401 before data access; arbitrary organisation query strings are ignored. Provider credentials remain in the existing server/GitHub secret stores.

On each successful read, the runner encrypts the list with AES256GCM into `.operations-alert-config.enc`; a unique per-run GitHub cache entry restores the latest available copy for future runs. Encryption key derivation is domain-separated from the bearer credential. No recipient details go into logs or result artifacts; reports contain channel, pseudonymous recipient reference and provider acknowledgement only. Four recipients are dispatched concurrently; independent channels preserve partial results and uncertain POSTs are never replayed automatically.

If the website/config reader is unavailable, the runner uses the encrypted last-known list (maximum age30days). GitHub cache storage is best effort and may evict inactive entries. If no valid encrypted copy is available, emergency notifications retain the existing confirmed Brett email/mobile GitHub variables. Changes, pauses and removals cannot reach an unavailable reader until it becomes reachable; allow the next successful monitor cycle to refresh the encrypted copy. The site should not be the sole place emergency contacts can be recovered. During key rotation, update both protected environments and verify a fresh configuration read/cache before relying on fallback.

Deployment uses the normal exact-main release checks and backup/build/versioned migration procedure. No new schema migration is required. Bootstrap only the confirmed Brett recipients; no invented team member or customer recipient. Verify anonymous admin/reader rejection, owner read/write, configuration source SAVED_RECIPIENTS in a real external monitor run and provider delivery of an explicitly labelled test. Isolated browser/SQL tests are separate evidence from live owner UAT and physical recipient acknowledgement.

Healthy silence, failure/recovery notifications and existing cooldown remain. This release does not make GitHub cron a guaranteed10minute SLA, add a second stopped-monitor watch, establish response/escalation timing or close backups, keys, provider/device UAT, staff training or business approval.


## Monitor transport and failure evidence (23 October 2026)

Monitor email uses the same verified-TLS Hostinger transport and fixed bookings@stor24.co.za sender as the application. Configure the existing SMTP app credential as the production environment secret STOR24_ALERT_HOSTINGER_SMTP_PASSWORD; keep its value out of source, logs and artifacts. Rotate this secret when rotating the server credential. The monitor no longer reads its old SendGrid secrets. Retain those until the new transport's live acceptance and inbox delivery are verified; reverting code to SendGrid does not restore email service while its authentication is rejected.

SMTP sends one recipient per message and never automatically retries an uncertain send. AUTHENTICATION_FAILED means a definite SMTP authentication rejection; UNCERTAIN means review provider/inbox evidence before any explicit resend. SMTP acceptance is separate from inbox delivery. The existing recipient selections, disabled recipients, emergency defaults, encrypted cache, cooldown and replay protection still apply.

Origin probes retry only transient transport failures, at most three attempts per plain/forged-header probe, with an eight-second connect and twelve-second request limit. A received HTTP response other than403 fails immediately; certificate verification failures are not retried. Timeouts remain unverified, never a successful protection check. SSH uses three connection-establishment attempts with strict host verification and bounded keepalives; it never replays a remote command after execution begins. Readiness has a ten-minute hard job deadline to accommodate its bounded probes.

Alerts use fixed public-validation names, exact allowlisted origin hostname/probe/HTTP or curl outcome, backup/resource markers and GitHub step metadata. Raw logs, response bodies and credentials never enter notification bodies. Both readiness and backup failures are reported when simultaneous. A failed monitor connection is distinct from a confirmed failed health/backup validation. Use the linked run for full job evidence. A labelled test sends to the configured operations team; it does not establish service health or outage duration.


## Independent network confirmation and partial response repair (23 October 2026)

A partial HTTP body from a failed transfer must not be concatenated with a successful retry. Public health now writes to a temporary regular file, which curl resets before each retry, and parses only the final completed response. It still checks service, application, database and the configured expiry worker; bodies are never logged and the file is removed on exit. Invalid completed JSON, failed health fields, unexpected origin HTTP responses and certificate failures remain failures, not candidates for a healthy override.

The primary external probe runs on an Azure-hosted Ubuntu runner. Only exhausted transient connection/transport errors trigger a new independent probe on GitHub's separate macOS cloud. That probe must freshly pass both public health and all eight plain/forged direct-origin403 checks. The final readiness job is the sole input to existing notifications and dashboard publication. A healthy confirmation records STOR24_MONITOR_PATH_RECOVERED in that run; it is actual independent evidence, not a timeout being treated as protection. Both paths timing out, missing/malformed output or a definite bad response still fail. The original primary evidence is retained in its job logs. This avoids replaying whole workflow attempts and masking original failures.

Backup/resource verification and alert/evidence publication also run on the separate macOS network: both jobs connect to the VPS, so moving only public readiness left SSH checks on the repeatedly failing original path. SSH host-key pinning, private key permissions, three bounded native connection attempts and real remote checks remain required. A timeout before those checks means verification is unavailable, not that a backup failed. A platform queue delay is still observable as missing/stale evidence; do not rerun away an original failure or weaken the firewall.

Monitor-specific PR validation runs the portable fixtures, real partial-body regression and actual public read-only probes on Ubuntu and macOS. It never uses production secrets, sends notifications or publishes dashboard status. Standard hosted runners are free for this public repository; no billing change is required. Neither this change nor successful recurrence establishes which upstream network operator dropped earlier connections. Do not change firewall allowlists to admit GitHub runners: direct-origin access must remain denied.


## Outbound host checks and independent evidence - 24 October 2026 (release pending)

Routine monitoring no longer needs VPS SSH: the existing public website/database/expiry-worker checks and eight direct-origin protection probes stay on external runners with independent network confirmation for transport-only failures. A root-owned systemd timer runs the existing read-only encrypted-backup/resource scripts locally every five minutes. A purpose-specific random 256-bit STOR24_HEARTBEAT_KEY authenticates fixed, bounded JSON reports to the existing Cloudflare worker at https://portal.stor24.co.za/_operations/monitor/host. No recipients, database records, provider credentials, raw logs or environment files enter the evidence store. The key grants only this evidence protocol, not administration or SSH access.

Cloudflare KV MONITOR_EVIDENCE retains the last report with an edge-observed receivedAt; the external GitHub backup job checks both that timestamp and checkedAt against a15minute freshness limit. A missing/stale report or unavailable store is a WARNING that server checks are unverified, never a fabricated backup failure/site outage. Concrete local check failures remain HIGH. At a ten-minute external cadence, notification occurs on the next completed observation after the freshness limit, not an exact15minute SLA. KV propagation and upstream scheduler/queue delays remain limits; complete Cloudflare or GitHub failures are separate provider dependencies.

GitHub posts only safeMonitorEntry aggregates to /_operations/monitor/dashboard. The host's same outbound timer downloads these and atomically updates the existing local dashboard history; no incoming SSH publication. Dashboard synchronisation can lag one five-minute tick plus KV propagation. Lost publication remains a failed GitHub job, and stale local dashboard evidence remains unverified. Existing notification recipients, encrypted last-known fallback, cooldown, no-replay policy and SMTP/Twilio transports are unchanged. Evidence reads/writes retry at most twice; provider sends do not gain retries.

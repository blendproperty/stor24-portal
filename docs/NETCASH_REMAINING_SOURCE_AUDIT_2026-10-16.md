## Important correction: original refund transaction ID is available in another source

The current [statement contract](https://api.netcash.co.za/standard-integration/netcash-statement/) identifies field3 as the numeric original Netcash transaction ID. parseDailyStatement validates and retains it as a string, SettlementLine.transactionId persists it, and netcashReceiptSource verifies the selected row against the checksum-protected balanced original raw statement. Thus absence from Pay Now status alone does not establish absence from the whole system. An eligible original positive PNC line can be a source for a future refund binding; a local Payment ID or RequestTrace cannot substitute.

The refund adapter accepts an xs:int-range transaction ID, while statement IDs permit up to30digits. A new workflow must validate the exact nonzero original decimal string against the actual refund API range before conversion, reject lossy/unsupported values and never truncate or use Number rounding. It must recheck raw statement integrity, exact merchant/payment binding and original amount/current refunds; a same-value description match is insufficient.

The [single-line refund contract](https://api.netcash.co.za/inbound-payments/pay-now/card-single-line-refund/) requires the refund to be authorised separately in the merchant frontend and limits it to the original statement value. API000 cannot become a completed payout. Code330 reports an existing refund request; it is not permission to issue a second request or assume no earlier processing. Its comma-decimal prose conflicts with the current WSDL xs:decimal representation; no real experiment or unverified format change is authorised here.

Existing settlement paymentProof rejects sandbox/test receipts for financial approval. A test-status card observation cannot be manufactured into a finance-reviewed live statement or cash payment just to make refund tests/controls eligible. New isolated fixtures may model a valid original source but must remain explicitly synthetic. Pending provider refunds must also interlock with recordRefundPayout and approved-refund cancellation under the same account lock before any real transport is exposed; otherwise a second manual payout can bypass an uncertain provider request.

## Important distinction: DebiCheck collection uses a separate published file contract

The current [DebiCheck batch contract](https://api.netcash.co.za/inbound-payments/dc/debi-check-2/) has its own instruction and fields for the original masterfile account, amount, tracking choice and approved bank contract. Standard compact two-day upload cannot be relabelled as it. Source authentication currently uses a UUID-derived32-character AccountReference; the collection table describes a22-character masterfile reference. The [TT1 page](https://api.netcash.co.za/inbound-payments/dc/debicheck-tt1-synchronous/) does not document the relationship or a positive length limit. This is a mapping/compatibility question to verify, not evidence that a32-character TT1 request necessarily fails. Never truncate the retained reference or invent a mapping to make a file fit.

Actual TT1/test payer approval remains absent per Brett's explicit answer. Even a future authenticated bank result is not independent authority to collect; the bank test consent and operator approval deliberately exclude collections. Draft preparation/review can remain blocked on the missing original mapping/mandate, with actual provider and finance gates visible.

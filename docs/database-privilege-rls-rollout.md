# Database privilege separation and RLS rollout — 2026-10-29

This is a staged candidate, not an instruction to change production. Production read-only catalog evidence previously identified superuser/BYPASSRLS application roles and zero RLS-enabled public tables. It does not establish external database exposure. The website has no direct database connection within this change's scope.

## Prepared change

`scripts/migrate-with-owner.mjs` starts Prisma migrations with `MIGRATION_DATABASE_URL` as the child process's `DATABASE_URL`. It requires a separate runtime URL, a distinct login name, and matching host, port and database; it removes `MIGRATION_DATABASE_URL` from the child environment. Keep that credential in a separate, access-controlled migration-only execution context; never put it into the application environment. The launcher is opt-in and the current production deployment does not invoke it. The CRM migrator image includes the launcher, but its default command and production Compose are unchanged.

## What was tested

The isolated `tests/integration/database-role-rls.test.mjs` requires explicit opt-in, localhost and a database ending `_ci`. It checks a runtime login without superuser, BYPASSRLS, role/database creation, role memberships, object ownership or schema creation. It creates and drops its own random synthetic table, exercises missing context, filtered reads, cross-scope insert/update denial and forced-owner behavior. Critically, it also demonstrates that the runtime role can change a custom tenant setting and impersonate another tenant. The test is not an application RLS policy or proof of production tenant isolation. A new isolated CI job runs it and the migration URL contract tests. The disposable role had broad table CRUD for compatibility, not a reviewed least-privilege grant matrix.

## Remaining design and rollout gates

1. Inventory every existing runtime, worker, provider, backup, reporting, maintenance and migration consumer and their necessary tables, sequences, functions, extensions, ownership and default privileges. Review transitive role memberships, public grants and schema CREATE. Assign named ownership and a separately protected migration identity; exclude schema and role administration from runtime identities. Future-object grants must account for the identity that creates each object. Do not assume a successful subset of tests proves the grant matrix is complete.
2. Prove the migration launcher, full release sequence, rollback, backup and restore using a production-representative staging database and both real workflow paths. Validate the actual historical migration baseline and full migrations. Configure separate secrets for the transient migration job without exposing them to the app. Retain the existing runtime credential and deployment image for a bounded rollback, with a separate custody and rotation plan. Check all consumers before revoking old authority.
3. Design RLS per table and real trust boundary, including unauthenticated requests, workers, pooled connections and transactions. A single shared application database role and client-set tenant value are not a trustworthy independent identity: SQL injection or a compromised application can change that value. Determine a non-forgeable identity/authorization mechanism and safe scoped transactions, handle connection-pool reuse and multi-tenant operations, and test absent/forged context, cross-tenant reads and writes, joins, background jobs and migrations. CMS public versus editor access also needs a trusted distinction; a permissive policy would not provide isolation.
4. Test policies with non-owner, non-BYPASSRLS runtime identities and explicit fail-closed behavior. Owners normally bypass RLS, superusers and BYPASSRLS roles always bypass it; FORCE RLS affects eligible owners but not superusers. Enable policies incrementally only after application paths, rollback and recovery are verified. Never enable RLS globally without policies: PostgreSQL defaults to denying access.
5. Separately approve the concrete production role/configuration/RLS change and maintenance window after staging evidence. Monitor permissions and login failures; independently verify expected access and absence of cross-scope access after cutover. Preserve recovery, data, privacy, provider, staff/customer/editor and device acceptance gates.

The prior RLS/role prototypes and this preparation change do not modify production grants, credentials, roles, policies or data. References: PostgreSQL 17 [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [role membership](https://www.postgresql.org/docs/17/role-membership.html), and [default privileges](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html).

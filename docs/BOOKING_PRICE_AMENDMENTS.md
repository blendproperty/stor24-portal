# Governed online booking quote changes

Staff use Reservations > Booking price review and load the exact existing booking reference. A proposal records the new monthly rent and negotiation reason without changing the current quote, sending a message or taking payment. Another authorised colleague reviews the original/proposed particulars and records an approval reference. Staff provide the customer review page through the store's agreed communication process; this feature does not automatically send an invitation.

The customer requests and verifies a fresh email code after approval. The resulting access token must match this booking, its unexpired identity session and a retained email-verification audit for this booking. Staff approval, another booking's verification, a proposal link alone or the staff cookie cannot replace customer acceptance. The customer sees old/new monthly rent, initial rent, unchanged goods and checkout totals, explicitly accepts the exact offer fingerprint and acknowledges that agreement signing and payment remain separate. Repeated identical acceptance is idempotent.

Acceptance updates the current unsigned booking price and its effective initial-rent snapshot in one transaction. The original snapshot, original unsigned document and proposed terms remain encrypted in ReservationPriceAmendment; a database trigger prevents alteration of that original evidence, proposal terms, request binding and deadline. Terminal evidence cannot be updated. The old unsigned signing token is invalidated, then the customer separately prepares/reviews the regenerated agreement. Card and EFT remain the two once-off choices. No payment, ledger entry, allocation, refund, mandate or provider request is created by quote acceptance.

Supported application requires an active online rental quote, current original hold, completed original contact verification, a valid saved snapshot, ZAR and no signed/converted/mandated/payment-started/financial history for the booking. Existing signed agreements and financial activity require the separate finance/legal amendment process. Hold/date/unit/customer/product/business/rental-plan/goods/document/account/source changes cause source review rather than silent repricing. The offer deadline never extends the original hold. Generic reservation edits cannot bypass protected saved online particulars. Facility, unit, reservation and customer locks follow the existing allocation order during acceptance; concurrent old-agreement signing and price acceptance cannot both accept different particulars. Audit failure rolls back quote, document token and proposal state.

Access requires reservation_prices.view, reservations.manage and billing.view in the same store. Proposing/withdrawing additionally requires reservation_prices.propose; independent approval/rejection requires reservation_prices.approve. No employee permission is assigned by the implementation. The customer page and endpoint are exact public routes; adjacent staff paths remain authenticated. Public requests are same-origin, size-bounded and rate-limited. Staff/API errors never return ciphertext or original private document content.

Verification evidence and release stages are recorded in PROJECT_CONTEXT.md. Intercepted browsers and synthetic database fixtures are not actual customer acceptance, delivered email/OTP, signature, receipt, legal approval or staff UAT.

The native enquiry/payment cohort report reads the first immutable original quote when accepted amendments exist. Separate fields show the customer-accepted change count, latest accepted monthly quote and acceptance time as of the report end date. They describe accepted unsigned quotes, not signed/effective rent or revenue. Original/proposed archive hashes, original identity, quote fingerprint, independent review and exact customer acceptance audit must agree across the full retained change chain and current quote. Missing, duplicated, foreign or inconsistent evidence holds the row and monetary totals. The source uses the same bounded repeatable-read transaction as the other cohort joins. The new actual PostgreSQL producer/report regression must pass protected CI before this integration can release. Signed/effective price amendments, invoice/finance reconciliation, original historical coverage, provider/email delivery, permission assignment, staff/customer/finance training and UAT remain separate gates. No production amendment, signature, payment or provider action has been performed by the agent.

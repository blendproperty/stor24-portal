# Merchandise hold expiry

The canonical authenticated fallback is `POST https://portal.stor24.co.za/api/v1/operations/merchandise-orders/expire`. Its existing dedicated `x-cron-key` authentication remains mandatory. Origin allowlists and callback exceptions are unchanged. GitHub's five-minute schedule is best effort and must not be the primary 20-minute hold timer.

The application includes an opt-in scheduler: `MERCHANDISE_APP_WORKER_ENABLED=true`. It starts through Next.js Node runtime instrumentation, runs immediately and every minute, prevents overlap within a process, and processes at most five 100-order batches per tick. Keyset progress survives subsequent ticks within that process, so inconsistent old rows do not starve later holds. Multiple app instances and the HTTP fallback remain safe through the existing order locks and transactional rechecks. A process restart begins a fresh sweep. Large backlogs may take multiple ticks; this is not a hard real-time deadline guarantee.

Only overdue AWAITING_PAYMENT orders are eligible. Reserved quantity is released atomically with EXPIRED status and an audit event. Physical stock is unchanged. Paid/fulfilled orders are excluded; an independently succeeded payment with stale awaiting status requires review and is left unchanged. Inconsistent stock/items roll back that order; the sweep continues. Late verified payment still follows existing PAYMENT_REVIEW/reconciliation semantics and cannot resurrect released stock.

`/api/health` returns customer-free aggregate worker state and 503 when an enabled worker has failures, has never completed, has not completed within five minutes, or a sweep remains unfinished for five minutes. Existing container checks observe this every 30 seconds; an unhealthy container is a signal, not an automatic remediation guarantee. The existing operations monitor requires an active healthy application worker when repository variable MERCHANDISE_EXPIRY_WORKER_ENABLED is true and feeds existing alerts. Those GitHub checks can also be delayed: independent external cadence, alert delivery and a named response owner still require acceptance. No independent service or persistent credential was introduced.

# Bounded deployment phase evidence

The existing verified-ref SSH deployment records structured `STOR24_DEPLOY_PHASE` lines in its normal GitHub Actions job log after the verified checkout. This is diagnostic evidence, not a retry, rollback, routing change or availability guarantee.

Each record contains UTC, the verified full commit SHA, an allowlisted phase, the last entered phase and the final exit status when available. At setup, before/after container replacement, healthy and exit it also attempts a fixed app-container snapshot: validated container ID, image digest/tag, state, health, OOM flag and localhost `/api/health` HTTP status. Values that do not match their closed formats become `unknown`. The helper never emits raw Docker inspection, environment values, request headers, response bodies, cookies, commands or application/proxy logs.

Docker and local HTTP reads have a three-second outer timeout; HTTP also has a two-second timeout. Captured Docker output is limited to512bytes and HTTP status output to4bytes. Failures are best effort and do not alter deployment success/failure. These snapshots add bounded diagnostic time to the existing deployment. Retention/access follows the existing private Actions job log; no new storage, public artifact or service is created.

The EXIT trap preserves the original shell status, including a failed command inside the existing `&&` list. It records the last entered phase before exiting with that same status. Deployment commands, their order, health checks and existing connection-establishment-only SSH retry remain unchanged. No deployment is replayed. A connection loss or host/process termination can prevent the final record; missing evidence is not success. Fetch/checkout failures occur before the newly checked-out helper can start and remain visible only in the existing job failure/log.

Actual Bash fixtures execute the remote workflow command chain extracted from the YAML with the real helper and stubbed system commands. They check success order; build, migration, replacement, health and final-curl exit preservation; absence of later work after failure; malformed/oversized/unavailable diagnostics; and a real bounded diagnostic timeout. Fixtures are isolated local files, not production deployment or availability tests.

The16October health alert's historical cause, exact duration and customer impact remain unproven. A single-container Docker-discovered router replacement is a supported hypothesis only. The new timeline may help correlate a future event; localhost health does not prove external proxy/CDN routing or customer reachability. Zero-downtime architecture, start-before-cutover, proxy configuration and resource sizing require a separate design/audit. No live infrastructure, provider, role, financial or customer action is authorised by this source change.

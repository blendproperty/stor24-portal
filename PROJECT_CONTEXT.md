# STOR 24 CRM and Operations Platform — Project Context

## HikCentral direct integration — regionIndexCode health-check bug found and fixed, 15 September 2026

- **Symptom:** "Test connection" for Store 1 - Midpoint in the Hikvision integration admin UI (`/settings/integrations/hikvision`, shipped 24 August 2026) failed with `{"code":"2","msg":"Incorrect request parameter. [regionIndexCode parameter error]"}` when the health check called the region-scoped `/artemis/api/resource/v1/acsDoor/advance/acsDoorList` endpoint using the commonly-documented placeholder region code `root000000`.
- **Methodology:** rather than guess further from documentation, built a standalone signed-request probe script (`hikcentral-probe.js`) and ran it directly against the live production HikCentral gateway (same approach previously used for the EMS project), reading the raw request/response instead of assuming behaviour.
- **Findings:** `root000000` is a documentation placeholder, not a universal region constant, and is rejected as an invalid region on this installation. `/artemis/api/resource/v1/regions` on this installation returns 76 flat, device-named regions with no meaningful hierarchy (`parentIndexCode: "-1"` for all) — there is no real "root region" to scope to. The plain (non-"advance") `/artemis/api/resource/v1/acsDoor/acsDoorList` endpoint requires no region parameter at all and was verified live to return the facility's real doors with just `{pageNo, pageSize}`.
- **Fix:** `src/lib/integrations/hikcentral-provider.ts` `health()` now calls the plain `acsDoorList` endpoint instead of the region-scoped "advance" search; the `HIKCENTRAL_ROOT_REGION_INDEX_CODE` constant and `regionIndexCodes()` helper were removed. `regionIndexCodes` remains on the configuration type as an unused, reserved field. Corresponding unit test in `tests/hikcentral-provider.test.ts` updated to assert the new URL.
- **Release evidence:** First attempt (PR #124, `root000000` fix) was superseded after live testing disproved it; a direct push to `main` outside PR #124's branch caused history divergence and a phantom conflict against this file. Resolved by branching `fix/hikcentral-drop-region-scoping` fresh off the then-current `main` tip and opening PR #125 ("HikCentral: drop region scoping from the health check (supersedes #124)"), containing the corrected provider fix and the corrected test. CI initially failed on the stale test assertion (270/271 passing); fixed and re-pushed. PR #125 merged to `main` 2026-09-15T08:09:33Z.
- **Live verification:** post-deployment, "Test connection" for Store 1 - Midpoint now returns "HikCentral connection verified for this facility" (green/Connected), last successful check 2026-09-15 10:25:25 SAST. This confirms the health check fix works end-to-end against the real gateway, not just in CI.
- **Face/biometric enrolment UI located and reviewed:** the enrolment and revocation UI lives at `/access` (`src/app/access/page.tsx`, component `src/components/biometric-access-workspace.tsx`). It is a page inside the existing admin/CRM portal, not a separate app: staff select an active tenancy from a dropdown, upload a JPEG/PNG face photo (max 5MB, plain file input, no live camera capture) with a required consent checkbox, and submit to `POST /api/v1/access/biometrics`, which forwards the image to HikCentral via `enrollBiometricAccess` (`src/lib/biometric-access-service.ts`) and stores only a SHA-256 hash of the image, never the raw photo. A register table below lists all enrolments with a Revoke action (`DELETE /api/v1/access/biometrics`) for ACTIVE entries.
- **Open gates before HIK-3 (live enrol/revoke test):** the Store 1 - Midpoint facility mapping still uses placeholder data — `organisationIndexCode: "TEMP-CONNECTION-TEST"` and door index codes 150/145/161/155/140/135/1004, which resolve on the HikCentral installation to generic Midrand Business Park vehicle-lane doors, not confirmed Stor24 storage-unit doors. User has confirmed this is acceptable to leave as-is for a first mechanical enrol/revoke plumbing test (proving person creation and permission grant/revoke works), provided those door codes are not live production doors someone could actually walk through during the test — this has not yet been independently confirmed. Real org index code and door index codes for Stor24-specific doors are still needed before HIK-3 is meaningful for production use. HIK-3 also requires at least one customer with an active tenancy/occupancy already in the system to select from the enrolment dropdown.

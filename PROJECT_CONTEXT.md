## Netcash Pay Now sandbox proof — 7 September 2026

- **Scope:** this closes a Pay Now-specific sandbox-proof slice only. It does not change Netcash's BLOCKED status in `docs/STOR24_OUTSTANDING_TASKS.md` item 1 or the Integrations screen's "Configuration required" state — per the governance boundary already recorded in `claude/invoicing-statements-scope.md` §0, moving those requires business sign-off in addition to sandbox proof, and this is a single-product, single-successful-transaction proof, not full failure-case, reconciliation or exception-ownership coverage.
- **Contract correction (implementation):** `src/lib/payments/netcash-client.ts`'s Pay Now functions were checked directly against Netcash's published Pay Now eCommerce and TransactionStatus/Check documentation and rewritten to match it: Pay Now is a **browser form POST** to `https://paynow.netcash.co.za/site/paynow.aspx` (fields `m1`/`m2`/`p2`/`p3`/`p4`/`Budget`/`m9`), not the server-to-server REST call originally scaffolded; `ReturnUrl`/`CancelUrl`/`NotifyUrl` are not per-request parameters, only a one-time NetConnector Profile configuration in the Netcash portal; `p2`/`p3` length limits (25/50 chars) are now enforced rather than silently truncated. Netcash defines no signature/hash scheme for the Notify postback, so `src/app/api/webhooks/netcash/route.ts` no longer trusts the posted body — it takes only `RequestTrace` and re-verifies server-to-server via a new `checkPayNowTransactionStatus()`; only that response can mark a `Payment` `SUCCEEDED`. This is the concrete, Pay Now-specific answer to Asana task `1217761345745722` ("confirm Netcash callback contract... verify provider signature against raw body"): there is no provider signature to verify, so authenticity comes from re-verification instead. Separately, the `ValidateServiceKey` SOAP namespace bug (data fields sent in the wrong DataContract namespace, causing every field to silently deserialize to null) was fixed and confirmed live against Netcash's real endpoint on 4 September.
- **Two further pre-existing bugs found and fixed while proving this live, neither introduced by the correction above:**
  1. `src/proxy.ts`'s session-auth allowlist (`publicApiPrefixes`) never included `/api/webhooks/netcash`, so Netcash's postback was rejected with 401 before it ever reached the handler, regardless of portal configuration. Fixed by adding the prefix, with a new regression test in `tests/auth-security.test.ts`.
  2. `getNetcashConnection()` in `netcash-client.ts` returned `IntegrationConnection.config` without decrypting its `*Encrypted` fields, so any real call to `createPayNowCheckout` failed closed with `NETCASH_PAY_NOW_SERVICE_KEY_MISSING` — for every Netcash product, not only Pay Now. Fixed by decrypting with the existing `decryptIntegrationSecret` helper before use. **This fix is proven working only in a disposable, throwaway test environment and has not yet been committed to `main`** — see open gates below.

## Sign-in security hardening — 19 August 2026

Brett asked for a security audit of sign-in/auth across all three repositories ("harden and secure the website for sign-in and prevent hacking"). Full audit findings and fixes below; this repository (the CRM, highest-privilege sign-in surface) was already the most solidly built of the three.

**What was already solid here, confirmed by direct code review (not assumed):**
- Custom JWT auth via `jose`, not a third-party auth library; bcrypt cost-12 password hashing.
- Double-layer authorization: `src/proxy.ts` middleware verifies the session on every request *and* independently re-checks `user.active`/`sessionVersion` against the database — a stolen or stale cookie doesn't survive a password change or deactivation.
- `src/lib/auth-guards.ts` (`requireSession`, `requirePermission`) does a second, independent DB-backed check per route with facility-scoped RBAC, not just a client-side gate.
- Login route: DB-backed rate limiting (5 attempts/15 min), constant-time comparison to resist user-enumeration timing attacks, all attempts audit-logged.
- Cookies: `httpOnly`, `secure` in production, `sameSite: lax`, 8-hour expiry — no token ever stored in localStorage.
- Password policy: 12+ characters, requires mixed case, digit and special character (`src/lib/validators.ts`).
- Server-to-server endpoints authenticate via SHA-256-hashed shared secrets checked with `timingSafeEqual` (separate path from the CSRF/Origin check below, unaffected by that change).

**Fixed this session:**
- **CSRF gap in `src/lib/request-security.ts`.** `sameOrigin()` previously returned `true` when the `Origin` header was simply absent (`!origin || allowed.has(origin)`) — a real bypass, since a crafted cross-site request that omits `Origin` would sail through. Browsers always send `Origin` on same-site mutating fetch/XHR/form requests, so the fix now requires `Origin` to be present and allow-listed for any non-safe HTTP method (`POST`/`PUT`/`PATCH`/`DELETE`), while leaving safe methods (`GET`/`HEAD`/`OPTIONS`) unaffected.
- **No security headers at the app layer.** Added `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, HSTS (`max-age=63072000; includeSubDomains; preload`) and a same-origin-only Content-Security-Policy in `next.config.ts` via `headers()`. This is the staff sign-in surface, so it got the strictest CSP of the three repositories (no external script/style/connect sources at all).

**Follow-up completed and live-verified 24 August 2026:**
- **Task 10 staff MFA/2FA is deployed and proven for the organisation owner.** Each authenticated staff user can enroll a standard authenticator app from Settings using a manually entered TOTP setup key. Enrollment does not become active until a valid six-digit code is verified. Authenticator secrets are AES-256-GCM encrypted at rest using a purpose-derived server key; eight recovery codes are shown once, stored only as keyed hashes, and consumed once. An enabled user receives no normal session after the password step: the server issues a five-minute HttpOnly MFA challenge and creates the existing eight-hour session only after a valid authenticator or recovery code. Login failures, enrollment, enablement, recovery-code use/regeneration and disablement are audit-recorded. Disabling requires both the current password and a valid second factor and invalidates existing sessions. CI and VPS deployment succeeded at commit `4a97bf4`.
